## New candidates

### S1-1: swarm members inherit another agent's unlabelled issue queue

- Source: `services/routing/_targets.py:118` and `config.py:349-362`.
- The queue fallback tests whether the repository has one owner, without
  checking whether the target is that owner. Swarm members carry the repository
  but are excluded from `owners()`.
- Reproduction: register `app` as owner of `acme/repo`, plus `scout` with that
  repository and a `swarm:audit` tag. GitHub returns unlabelled issue 42.
  `owners()` returns `[app]`, but `list_open_queue_for_target(..., "scout", ...)`
  returns `[42]`. The idle monitor can deliver it through `jobs/pending.py:119`.
- Verified with the actual queue helper and mocked GitHub listing.
- Suggested change: require the sole owner's name to equal the target; retain
  explicit `for:scout` lookup. This closes a queue-path gap in the #137 ownership
  exclusion, rather than reinstating its already-fixed event-routing finding.

### S1-2: age stamping creates duplicate queued direct messages

- Source: `services/jobs/retry.py:100,176-179`,
  `services/routing/_format.py:53`, `services/database/_queue_repo.py:43`.
- A drain stamps `(queued N min ago)` before re-offering a message. If delivery
  remains blocked, it enqueues again. `_source_key_of` preserves only `src:`
  identities; ordinary messages use a `msg:` hash of sender and original text.
  The aged text has a different hash, so it inserts another row instead of
  folding into the existing leased row.
- Reproduction: enqueue one direct message from Alice, backdate it three
  minutes, and drain while the target is busy. Actual SQLite in-memory execution
  changes `pending_count` from 1 to 2. Repeated drains at different ages can add
  more copies, which later become repeated deliveries.
- Suggested change: preserve the complete stored identity, or make a drain
  attempt unable to enqueue another copy of its existing row. Test repeated
  blocked drains of a message older than two minutes.

### S1-3: failed issue work is delivered after reassignment

- Source: `services/jobs/retry.py:139-164` and the issue branch of
  `drain_message_queue` in the same file.
- Retry fetches the current issue but does not validate that the old target is
  still in its audience. A loaded queue scope only restricts the acknowledgement
  gate; it does not validate the candidate itself. The drain also lacks that
  validation.
- Reproduction: an issue was queued for offline `app`, then relabelled
  `for:other`. Mocked GitHub returns the current reassigned issue and an empty
  current queue for `app`. `retry_delivery` still calls delivery for `app` and
  returns `retried`. Verified with the real retry function and in-memory DB.
- Suggested change: retire stale work in both retry and drain. Check current
  routing rather than blindly requiring queue membership: explicit targets in
  another repository can be valid even when it is outside their tracked queue.

### S1-4: the monitor defeats self-notification suppression

- Source: `services/routing/_router.py`, `_dispatch_issue` sender check;
  `services/routing/_targets.py:93-129`; `services/jobs/pending.py:111-130`.
- Initial dispatch suppresses an issue whose `from:` equals the target. Queue
  listing and the idle monitor do not apply that rule.
- Reproduction: sole owner `app` opens an unlabelled `from:app` issue. Initial
  event dispatch skips it, but the next idle monitor tick can send it back to
  `app`. Actual pending-loop execution with mocked GitHub and terminal delivery
  returned `{"app": "delivered_#6"}` for that issue, with no acknowledgements.
- Suggested change: consistently exclude the sender from work queues. Test the
  event-to-monitor sequence, including explicit `for:app` plus `from:app`.
- This contradicts the sender-never-gets-own-issue rule in
  `docs/how-it-works.md`.

### S1-5: a transient queue write failure permanently loses a GitHub comment

- Source: `services/routing/_delivery.py`, `_enqueue` and `finish`;
  `services/routing/_router.py:82`, `_deliver`;
  `services/routing/_ingest.py:102`, `_store_route_mark`.
- `deliver` correctly returns a blocked outcome with `queue="failed"`, but
  GitHub dispatch uses `safe_deliver`, which returns only the outcome. Ingestion
  subsequently marks the event processed despite neither paste nor durable
  queue storage succeeding. Subsequent copies deduplicate against that event.
- Reproduction using real SQLite in memory, a mocked busy profile, and a failing
  `db.queue.enqueue`: first result `dispatch: 0 delivered, 0 offline, 1 deferred`;
  pending queue count 0; event `processed_at` set; retry result
  `deduped: event test-comment already stored`.
- Suggested change: propagate failure to store GitHub delivery work so the event
  remains replayable. Account for partial multi-recipient success, since replay
  can otherwise repeat an already-delivered comment. Direct-message API callers
  already receive truthful storage status.

### S1-6: the work queue silently stops at the first 50 open items

- Source: `services/routing/_targets.py:115-123`;
  `services/github/interface.py:344`, `list_issues`;
  `services/jobs/pending.py:111`.
- Queue construction uses `list_issues` with its default `per_page=50`. That
  method fetches one page, oldest-created first. Priority sorting and
  acknowledgement filtering happen only after this truncation.
- Concrete sequence: the first 50 open issues have been acknowledged but remain
  open; issue 51 has not been acknowledged. The monitor skips every returned
  issue and never sees issue 51. A blocking item on page two is also excluded
  from priority ordering and close-then-next selection.
- Source validated, without an external GitHub test.
- The earlier audit deliberately preserved bounded `list_issues`; this is a
  distinct queue-call-site requirement. Retain that bounded API if needed and
  give routing a complete paginated queue listing.

## Previously open recommendations, revalidated

1. **Durable polling cursor:** `jobs/github_poll.py:110-124` initializes its
   restart window from `events.last_time_by_repo()`, which records receipt time,
   not GitHub source time. Processing part of an old backlog today and restarting
   can skip remaining old activity before today minus two minutes. Persist a
   source cursor only after a complete successful batch, or persist replayable
   event payloads. The process-local `_since` dictionary cannot provide this.
2. **Per-session delivery serialization:** `routing/_delivery.py`, `deliver`,
   has no lock spanning queue gate, readiness, paste and submission. Two distinct
   issues can both observe no unacknowledged work before either records delivery.
   A lock must cover the gate too. Coordinate queue-drain claims/order with the
   same transaction boundary; a named tmux buffer alone solves a different race.
3. **Retry retirement and isolation:** `jobs/retry.py:139-152,192-199` returns
   `acknowledged`, `no_repo`, or `issue_closed` without retiring the failure.
   `DeliveryRepo.failed` repeatedly selects the oldest retryable rows, limited to
   20. Terminal failures can occupy the window indefinitely. A queue-scope fetch
   exception also escapes the retry loop before its direct-message drain. The
   coordinator independently confirmed these two cases in its assignment.
4. **Telegram topic override consistency:** `_topic_discovery.py`, `agent_topic`,
   scans config then raw discovery. For config `{7: B}` and discovery `{7: A}`,
   incoming thread 7 routes to B but A's replies still select thread 7. Outbound
   resolution should use the merged config-wins mapping.
5. **Telegram group scoping:** `_topic_discovery.py`,
   `process_message_for_discovery`, allows any allowlisted supergroup to replace
   the global discovered group ID. `_routing.py` resolves by thread ID alone.
   Two allowed groups can reuse a thread ID and route into one another's agent
   topics. Bind mappings to their group, reject mismatched groups, and handle a
   configured group change without reusing old discovered thread IDs.
6. **Telegram sender identity:** `interface.py`, `_sender_tag`, returns the
   lowercased first name, and topic messages and `/tell` pass it as queue sender.
   Two people named Alice sending identical text collide. Retain readable display
   text if desired, but use stable Telegram user IDs for queue identity; the
   existing `_commands._who` already demonstrates that separation for audit.
7. **Grace period wiring:** `_intelligence.py:132-133` needs `idle_since`, while
   production delivery callers omit it. Wire authoritative idle timing, taking
   care not to compare a wall-clock hook timestamp with `time.monotonic()`.
8. **Plan escalation storage truth:** `check_plan_waiting` used `outcome_queues`
   to suppress repeat notification even when storage failed. Use
   `deliver().queued`. At the time this report was written, the coordinator's
   uncommitted changes already implemented that replacement; this scout did not
   edit or commit those files.
9. **Shared queue snapshots:** dependency sync, pending delivery, offline counts
   and lifecycle selection repeatedly request overlapping GitHub queues. A
   scoped per-tick snapshot reduces requests and avoids internally inconsistent
   selection, while readiness must still be checked immediately before delivery.
10. **Priority inputs:** `_targets.py:128` never supplies `dependents_count` to
    `compute_priority_score`; `_priority.py` substitutes issue number for age
    even across repositories. Documented dependent/age priorities need real
    inputs or a narrower documented contract.
11. **Integration registration:** `_registry.build_integrations` and
    `_notify._STATIC_NOTIFIERS` independently register vendors. One registration
    source would prevent adding a lifecycle integration without its notifications.

Suggested order: repair durable event/queue loss and duplication; serialize
delivery; scope Telegram identity/routes; retire and isolate retries; complete
and reuse queue listings; then wire grace/priority inputs and consolidate
integration registration. Broader schema or delivery-receipt decisions should
remain explicit recommendations when they do not fit this PR.
